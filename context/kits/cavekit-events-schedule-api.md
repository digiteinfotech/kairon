# Cavekit: Events Schedule API

## Scope
A new JSON scheduling endpoint on the existing Python events server, so the events server is the single writer of scheduled jobs. Both the port's and the Python action server's schedule_action submit jobs through it. This is the only kit that changes the Python codebase.

See context/refs/research-brief-java-action-server-port.md for evidence.

## Requirements

### R1: Scheduling endpoint
**Description:** The events server accepts a JSON scheduling request and writes the job through its own scheduler job store.
**Acceptance Criteria:**
- [ ] [GAP] The endpoint is `POST /api/events/schedule/action`
- [ ] [GAP] The JSON body has exactly these fields: `job_id` (string, 32 lowercase hex characters, generated by the caller), `run_at` (ISO 8601 date-time string), `timezone` (IANA zone name, may be empty for the server's local zone), `schedule_action_type` (`pyscript` or `flow`), `schedule_action` (callback name or flow name), `bot` (string), `user` (the sender id), `data` (object of resolved params)
- [ ] [GAP] A successful request returns HTTP 200 with the events server's standard envelope (`success: true`, `message`, `data`, `error_code: 0`) and `data.job_id` equal to the submitted `job_id`
- [ ] [GAP] A second request with the same `job_id` is rejected with HTTP 200 and the standard error envelope (`success: false`, `error_code: 422`, `message`) and writes no second job document
- [ ] [GAP] A valid request results in exactly one job document in the scheduler job-store collection (`events.scheduler.collection` in the `events.queue.name` database) with `_id` = the job id
- [ ] [GAP] The stored job has executor `default`, `misfire_grace_time` 7200, `coalesce` true, `max_instances` 1, name `execute_task`
- [ ] [GAP] The stored job's function and arguments equal those of a reference job document captured from today's schedule_action direct write for the same inputs; the reference documents (one pyscript, one flow) are captured and stored as fixtures before R5 removes the direct write
- [ ] [GAP] The endpoint path and body schema above are documented in the events server's API docs
**Dependencies:** none

### R2: Execution equivalence
**Description:** A job created via the endpoint runs exactly like one created by today's direct write.
**Acceptance Criteria:**
- [ ] [GAP] For the same inputs, the endpoint-created job and a direct-write job produce the same `next_run_time`
- [ ] [GAP] When due, an endpoint-created pyscript job executes the same task with the same arguments as a direct-write job
- [ ] [GAP] When due, an endpoint-created flow job executes the same task with the same arguments as a direct-write job
**Dependencies:** R1

### R3: Dispatch wake unchanged
**Description:** The existing wake endpoint keeps working.
**Acceptance Criteria:**
- [ ] `GET /api/events/dispatch/{id}` for an endpoint-created job returns the same response as for a direct-write job
**Dependencies:** R1

### R4: Validation and auth posture
**Description:** Invalid requests are rejected with the events server's existing error envelope.
**Acceptance Criteria:**
- [ ] [GAP] A request missing any required field is rejected with HTTP 200 and the events server's existing error envelope (`success: false`, `error_code: 422`, `message`) and writes no job
- [ ] [GAP] A request with a schedule type other than `pyscript` or `flow` is rejected the same way and writes no job
- [ ] [UNVERIFIED] The endpoint has the same authentication as other events endpoints (none beyond network isolation) (needs human review)
**Dependencies:** R1

### R5: Single writer migration
**Description:** The Python action server's schedule_action also switches to the endpoint.
**Acceptance Criteria:**
- [ ] [GAP] The Python schedule_action no longer inserts into the scheduler job-store collection directly
- [ ] [GAP] The Python schedule_action submits jobs through the R1 endpoint
- [ ] [GAP] Existing Python schedule_action tests pass against the endpoint-based flow
**Dependencies:** R1

## Out of Scope
- Any change to the port (cavekit-orchestration-actions.md R2 consumes this endpoint)
- Changes to scheduler execution, `message_broadcast` or `analytics_pipeline` scheduling
- Authentication additions to the events server
- prompt_action, database_action, Lambda transports, LLM rephrase, native image
